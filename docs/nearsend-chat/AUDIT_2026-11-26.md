# Nearsend Chat iOS: audit, 26 Nov 2026

Scope: the iOS app in `NearsendChatiOS/` (SwiftUI, iOS 17+, about 5,700 lines, no third-party dependencies).
Method: full code review of the Bluetooth, routing and app-state layers; automated protocol tests (`Tests/main.swift`);
simulator runs (iPhone 17 Pro, iOS 26.5). **No Bluetooth was tested physically in this audit.** The iOS Simulator
has no Bluetooth ("unsupported"); every Bluetooth result below is from code review or simulated network tests unless it says
"reported by the owner on real phones".

## Executive summary

- **Overall:** the architecture is sound and small: one transport (`BLETransport`), one router (`MeshRouter`), one app
  store (`MeshService`). Encryption uses Apple's CryptoKit correctly. Texts work between real phones.
- **Main finding (P0):** photos and voice notes could never be sent over the most-used Bluetooth link. Each photo piece is
  a 1,200-byte packet, written in one Bluetooth write, but iOS and Android accept at most 512 bytes per write. This matches
  the owner's report ("audio stuck on waiting, text works"). **Fixed** (fragmented writes), with tests. Needs build 9 and a
  real two-phone test.
- **Security (P1):** a nearby attacker could replace a known contact's key by announcing that contact's id with their
  own key, so new messages would be encrypted to the attacker. **Fixed** (keys are pinned per id), with a test that fails
  without the fix.
- **Reliability:** connection attempts never timed out, so a phone that left mid-connect could never be found again until
  Bluetooth restarted. **Fixed** (20 s timeout).
- **Verdict: NEEDS IMPROVEMENT.** Functional, with the main known bugs fixed in code, but the fixes are not yet verified on
  real phones, and background behaviour plus three-phone relaying have never been tested on devices.

## Bluetooth audit

| Area | Finding | Evidence |
|---|---|---|
| Activation | `start()` is idempotent (guarded by `central == nil`); managers are created once; scanning starts only in `centralManagerDidUpdateState` when `.poweredOn`; advertising only after the service is added, when the peripheral manager is `.poweredOn`. Good. | Code review |
| States | poweredOn → "ready", poweredOff → "off", unauthorized, unsupported shown; resetting and unknown both shown as "Starting Bluetooth…". Adequate. | Code review, simulator ("unsupported") |
| Deactivation (Mesh switch off) | `stop()` invalidates the timer, stops scanning, cancels connections, fails pending writes, stops advertising, removes the service and releases both managers. Idempotent. **Bug:** people known through relays came back after pausing. **Fixed.** | Code review |
| Bluetooth off at system level | Links were not cleared because iOS does not always report each disconnect, so people stayed listed. Fixed earlier today (`dropAllLinks`, `forgetEveryone`). | Owner report, code review |
| Rapid toggling | Start, stop, start creates fresh managers each time; no duplicate scans because a stopped transport has no managers. No retained timers. **Not stress-tested**: needs a device. | Code review only |
| Scanning | One scan session, filtered by service UUID, no duplicates option (iOS background-friendly). Restarted after each disconnect so returning phones are found again. | Code review |
| Connections | **Bug:** CoreBluetooth never times out `connect()`. A phone that walks away mid-connect left a stale entry that blocked rediscovery of that phone. Also a device without our service stayed connected forever. **Fixed:** links not ready within 20 s are cancelled. | Code review |
| Writes | **P0 bug:** writes to an "out:" link sent whole packets in one write; iOS caps a write at 512 bytes. Photo and voice pieces are 1,200 bytes, so they always failed on that link (the router prefers it). **Fixed:** packets over 512 bytes are fragmented with the existing framing; small packets are unchanged, so older versions and Android still understand texts. | Test: "a photo chunk packet (1200 bytes) needs fragmenting" |
| Notifications ("in:" links) | Already fragmented to the negotiated size, with flow control (`peripheralManagerIsReady`). Good. | Code review, framing tests |
| Background | `bluetooth-central` and `bluetooth-peripheral` modes with state restoration for both managers. Matches what the code does. iOS limits: background advertising drops the service UUID to the overflow area (other iPhones can still find it while scanning for the UUID); scanning is slower; nothing works after a force-quit. | Code review; **not device-tested** |
| Battery | RSSI read every 6 s (15 s in Low Power Mode); no continuous duplicate-scanning; one timer. Reasonable. | Code review |

## Bugs found and fixed in this audit

| Bug | Severity | Root cause | Fix | Test result |
|---|---|---|---|---|
| Photos and voice notes stuck on "waiting" | P0 | One Bluetooth write over the 512-byte limit | Fragment writes over 512 bytes; reassemble per sender (`WriteFraming`) | 7 new checks pass; real phones: **pending build 9** |
| Contact key could be replaced by an impostor | P1 | Announcements overwrote known keys | Refuse a different key for a known id (`keyConflicts`) | New check passes; fails without the fix |
| Phone never found again after a failed connect | P1 | No connection timeout | Cancel links not ready within 20 s | Code review (needs device) |
| Relayed people reappear after pausing the mesh | P2 | Router kept relayed peers | `forgetEveryone()` on pause | Code review |

Fixed earlier today (also not yet on a device build before build 8): lost receipts (retries and re-answering repeats),
photo/voice retry and labels, Bluetooth-off list clearing, Erase-everything restarting Bluetooth on the first onboarding page.

## Changes made in this audit

- `Sources/Mesh/Framing.swift`: new `WriteFraming` (split writes over 512 bytes; fragments never start with "{").
- `Sources/Mesh/BLETransport.swift`: fragmented writes on "out:" links; per-sender reassembly of written fragments; 20 s
  connection timeout; cleanup of reassembly state on stop, Bluetooth off and unsubscribe.
- `Sources/Mesh/MeshRouter.swift`: refuse a different key for a known id (both announcements and direct links).
- `Sources/Mesh/MeshService.swift`: pausing the mesh forgets relayed people too.
- `Tests/main.swift`: write-size and fragmentation tests; impersonation test.

## Security findings

- Good: CryptoKit X25519 + HKDF-SHA256 + ChaCha20-Poly1305 with the message id as associated data; private key in the
  Keychain (`AfterFirstUnlockThisDeviceOnly`); no message text in logs; no network code, no analytics.
- Fixed: key replacement by an impostor (above).
- Known limits (document, do not hide): no forward secrecy (static keys); delivery and read receipts are not authenticated,
  so a relay could fake "delivered"; Nearby channel, announcements and SOS are public and unauthenticated by design; trust
  on first use until people verify fingerprints. The app already says it is not security audited.

## Performance findings

- Small, efficient: one 3 s timer, one scan, packets under 1.2 KB, photos about 14 KB, voice about 1.5 KB/s.
- Watch: `ForEach` with `messages.firstIndex` per bubble in group chats is O(n²) for long group threads; fine below a few
  hundred messages.

## Remaining problems

- All Bluetooth fixes are **unverified on real phones** until build 9 is installed.
- Android does not fragment writes yet (photos/voice to and from Android still fail on that link).
- No automated Bluetooth lifecycle tests (hardware needed); rapid-toggle stress not run.
- Background delivery with the screen locked has not been measured on devices.

## Device test checklist (two or three iPhones with build 9)

1. Both phones: Bluetooth on, Airplane Mode on, app open. Each sees the other on Nearby within 10 s.
2. Send a text both ways: "Delivered" ring appears; open the chat on the other phone: "Read".
3. Send a photo, then a 10 s voice note: both arrive and play; sender shows Delivered.
4. Toggle **Mesh** off and on 10 times quickly on one phone: the other phone disappears and reappears; no duplicates.
5. Turn Bluetooth off in Control Centre: the list empties; turn it back on: the other phone returns within 20 s.
6. Walk out of range for 1 minute and come back: the phone is found again (connection timeout fix).
7. Lock one phone, send it a text: notification with the hop sound arrives (background).
8. Three phones in a line (A–B–C, A and C out of range): a text from A reaches C showing "2 hops".
9. You tab → Share debug log after any failure, and send it to me.
